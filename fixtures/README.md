# Fixture corpus

`fixtures/pages/` contains representative Page Specs. They are the compiler's
specification: a capability is not complete until a fixture exercises it, and
every milestone adds to this corpus rather than to a private scratch file.

## Page classes

| Fixture | Class | What it forces the compiler to handle |
| --- | --- | --- |
| `plan.yaml` | Implementation plan / plan review | Nested sections, ordered steps, timeline, comparison table, embedded diagram adapter, callout severity |
| `explain.yaml` | Code/system explanation | Long-form prose, code blocks with copy action, tabbed alternatives, alert levels, inline diagram |
| `recap.yaml` | Progress recap | Stats, timeline of events, card grid, sparkline/line chart, list with badges |
| `diff.yaml` | Change review | Table with status semantics, side-by-side comparison, risk matrix, collapsible detail |
| `dashboard.yaml` | Metrics dashboard | Every chart type (bar, line, area, pie/donut, sparkline, progress), KPI semantics, responsive grid |
| `media.yaml` | Media gallery | Local image gallery, network-denied video/audio degradation to poster plus link, carousel |
| `interactive.yaml` | Interaction coverage | Buttons, slider, carousel, tabs, accordion, copy, filter/search, theme toggle, dialog |
| `rich-composition.yaml` | Nested composition | Tabs, accordion, carousel and bento items holding charts, tables, code and other blocks; readable without scripts and in print |
| `responsive-layouts.yaml` | Responsive layout | 12-track grid items with tablet and mobile spans, `sidebar-layout`, `main-aside`, `rail-layout`, reflow down to a phone |
| `data-tables.yaml` | Typed tables | `data-table` columns of every type bound to a shared dataset, sort, search, sticky header, phone cards |
| `charts-v2.yaml` | Bound charts | Every chart kind from shared datasets through encodings, with markers, annotations and axis formats |
| `controls.yaml` | State and controls | Every native control bound to `state`, `visibleWhen` view switching, script-off initial view |
| `engineering-widgets.yaml` | Engineering status | Kanban, roadmap, test results, log viewer, API endpoint, schema viewer |
| `evidence-widgets.yaml` | Evidence report | Benchmark comparison, metric breakdown, annotated image, references |
| `product-widgets.yaml` | Product page | Pricing, feature matrix, testimonials, logo cloud, people, calendar, gallery lightbox |
| `theme-dialects.yaml` | Theme recipes | A preset's component recipes, with one recipe overridden in the spec |
| `theme-showcase.yaml` | Theme coverage | One content spec compiled under every built-in preset into `fixtures/snapshots/` |
| `showcase.yaml` | Landing page | Showcase blocks (bento, marquee, terminal, file tree, KPI, checklist) with real screenshots and a recording |
| `brainstorm.yaml` | Decision record | An accepted direction with the alternatives that were weighed |
| `all-components.yaml` | Roster coverage | Every block type of the original Page Spec v1 roster in one page |

### Composition pages

Six pages combine many blocks the way a real report does. Each one validates
with no warnings and compiles to identical bytes three times
(`tests/unit/fixtures.test.ts`), and `tests/browser/composition-matrix.spec.ts`
checks every fixture page across widths, schemes, reduced motion, script-off,
print, keyboard focus, network and axe.

| Fixture | What it combines |
| --- | --- |
| `complex-dashboard.yaml` | `data-console`, a 12-track grid, KPIs, stacked and line charts and a data table from one dataset, `main-aside` |
| `benchmark-report.yaml` | Benchmark comparison, a waterfall, a data table with percent and sparkline columns, tabs, references |
| `research-report.yaml` | `research-notebook`, a sidebar layout, an annotated image, a metric breakdown, a rich accordion, references |
| `product-case-study.yaml` | `product-studio`, a hero, a testimonial, pricing, a feature matrix, a gallery with lightbox, a logo cloud, people |
| `interactive-data-explorer.yaml` | Page state, a filter-bar over a data table, a `visibleWhen` metric switcher, charts on the same dataset |
| `incident-report.yaml` | `executive-report`, a timeline, a log viewer, test results, an API endpoint, a kanban, a roadmap |

`fixtures/rejected/` holds specs that must fail: the top-level files are
injection attempts that fail with `POLICY_VIOLATION`, and `validation/` holds
well-formed but wrong specs that fail validation with a located diagnostic
(`tests/unit/rejected-validation-fixtures.test.ts`). An optional first line
`# expect: CODE $.path` pins the expected code and path. `fixtures/snapshots/` holds the theme showcase compiled
under every built-in preset, one file each, regenerated by
`pnpm snapshots:generate`.

## Rules for fixtures

- **Semantic blocks first.** Use a semantic block whenever one expresses the
  intent; reach for primitives only to show the escape hatch.
- **No network in a default fixture.** Network-backed behavior is exercised with
  an explicit `policy.network` opt-in, in `media.yaml`, so the offline default
  keeps a fixture of its own.
- **Deterministic content only.** No dates that change per run, no random
  identifiers, no locale-dependent values. Fixtures feed byte-comparison tests.
- **Small but representative.** A fixture demonstrates a contract; it is not a
  demo page. Prefer the smallest spec that still exercises the contract.
- **Every fixture declares `version`, `meta`, `theme`, and `policy`.** Those four
  are the normalizer's minimum viable envelope.

## Fixtures are also benchmark input

The same specs feed the legacy-versus-AK-Render comparison: the content is
constant across the two implementations so the comparison measures presentation
cost rather than content differences.
