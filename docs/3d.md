# 3D blocks

Fourteen 3D blocks describe scenes, objects, effects and data as typed props.
The compiler inlines one shared three.js runtime (generated by
`pnpm three:generate`, checked by `pnpm three:check`) only on pages that use a
3D block, so the page stays offline and deterministic, and every block also
compiles to static content that reads without JavaScript or WebGL.

## Recipes

Each recipe has a minimal spec, a full spec, a state-binding page and the
fallback. Every YAML example in these files compiles;
`tests/unit/docs-3d-examples.test.ts` checks them.

## Finding a 3D block (for agents)

Read as little as the task needs:

1. `ak-render catalog` lists the 14 blocks as one `3d` family line, not 14
   entries. Families exist so the catalog stays inside its byte budget
   (`tests/unit/catalog-budget.test.ts`) as the roster grows; members are full
   blocks everywhere else.
2. `ak-render search-catalog 3d <intent words>` ranks the members, for example
   `search-catalog 3d globe` or `search-catalog 3d scatter`.
3. `ak-render describe <type> [<type>...] --compact` gives one line per prop for
   the blocks you use. `describe <type> --json` is the full contract.
4. Open the recipe for that block above only when the compact contract leaves a
   question (state paths, fallbacks, limits).

The MCP tools `catalog`, `search-catalog` and `describe` return the same
surfaces. There is no 3D page recipe in `ak-render recipes`: those are whole
page kinds, and a 3D block is one block inside such a page.

## Shared contract

- `summary` is required on every block except `text-3d`, whose `text` is the
  label. It is the text alternative of the live canvas.
- Inputs are closed vocabularies and bounded numbers. There is no shader,
  script or raw asset input: `shader`, `glsl`, `wgsl`, `vertexShader`,
  `fragmentShader` and prototype keys are rejected anywhere in a spec.
- Diagnostics carry the prop's JSON path, the reference the author wrote and a
  `details.fix`.

### State

A 3D block joins page state the same way an HTML control does
([data and state](data-and-state.md)):

- `bind` (and the block's other `*Bind` props) names a `state.<key>` path. A
  pick in the scene writes the chosen id there through the closed `set-value`
  action; a `select` or any other control bound to the same path drives the
  scene back. The initial `state` value is applied at compile time, so the
  static fallback shows it too.
- Only discrete choices reach state: an object, point, place, variant, filter
  or milestone id. Camera moves, hover and per-frame values never do, so state
  is not flooded and a page cannot loop on itself.
- `particles-3d` and `text-3d` have no state; they decorate.

### Fallbacks

The compiler projects every scene through the same camera as the live view and
emits a labelled SVG drawing plus the block's list or table. That is what
readers get without JavaScript, without WebGL 2, in print and in screenshots of
the source; each recipe names its own. With reduced motion the live scene
renders a still frame and every camera move is a jump. Boxes, including a
model's bounds, are drawn as their camera-facing faces with light shading, so
the plan reads as a solid.

`export3dPosterSvg(spec, { blockId, scheme, labels, modelResolver })` returns
that drawing as a standalone, deterministic SVG with its own styles. `scheme` is
`light`, `dark` or `auto` (both palettes, following `prefers-color-scheme`);
`labels: false` drops text for thumbnails. The gallery's 3D cards use it.

### Runtime

`window.akRender3d` exposes `mountAll`, `unmountAll`, `stats`, `freeze`, `sync`
and `ready` for tests and tooling. Scenes pause offscreen, recover from context
loss and release shared geometry on unmount. Each block reports
`data-ak-3d-state` (`static`, `loading`, `ready`, `error` or `unsupported`).

The quality profile is `low` on a coarse pointer or at most 4 CPU cores, else
`high` (`qualityProfile` in `src/blocks/three/runtime/entry.js`); low drops the
pixel ratio, shadows and antialiasing. `html[data-ak-3d-quality="low|high"]`
overrides it. Lower quality reduces decoration, never the data, labels or
controls. Where a block draws fewer items to stay fluid (`particles-3d`, the
`point-cloud-3d` budget), the data blocks state the drawn count and every item
stays selectable.

## Assets and network

Model files are opt-in through the `models` network capability. The compiler
never fetches a remote URL; only the browser does, and only when
`policy.network.allow` lists `models` (and the host passes any `providers`
list). Allowed model origins open CSP `connect-src`, since glTF loaders fetch
them; images stay in `img-src`. With no `models` origin, `connect-src` stays
`'none'`. There is no wildcard and no `unsafe-eval`. On a model page CSP adds
`connect-src data: blob:` plus allowed model origins, and `blob:` plus those
origins in `img-src`.

Local models are inlined by `resolveModelAsset` (`src/assets/model-assets.ts`,
Node only) as data URIs, so the page stays offline:

- Paths resolve against the spec's directory. Absolute, UNC and drive paths,
  `..` escapes (raw, backslashed or percent-encoded) and symlinks or junctions
  that leave it are rejected (`POLICY_VIOLATION`). A missing spec directory has
  its own diagnostic.
- `.glb` or `.gltf` only. A glTF's buffers are `.bin` files or
  `application/octet-stream` data URIs; its images are PNG, JPEG or WebP,
  checked by magic bytes for files and data URIs alike, and any
  `images[].mimeType` must be one of those. A GLB must be self-contained.
- `MODEL_ASSET_LIMITS` caps each file (16 MiB) and each page (32 MiB)
  (`SPEC_BOUNDS_ERROR`). Files are read through a descriptor, never more than
  the cap plus one byte.
- `asset.version` must be `"2.0"`. A remote URI inside a glTF passes the same
  `models` gate.
- `extensionsRequired` is checked against `SUPPORTED_GLTF_EXTENSIONS` (the KHR
  and EXT extensions GLTFLoader handles natively). Draco, Meshopt and KTX2
  decoders are not bundled, so such a model fails with a diagnostic that names
  the missing decoders. A problem inside a glTF also names its `gltfPath`
  (e.g. `buffers[0].uri`).

`compile` in the CLI and the MCP `render`/`compose` tools inject
`createModelResolver(specDir)` and `createPointCloudResolver(specDir)` through
`RenderOptions`; `render.ts` itself stays free of Node built-ins. Without a
resolver a local model fails ("needs a compile from a spec file"); a remote one
passes through. Point-cloud files follow the same directory sandbox, with
their own limits ([point-cloud-3d](3d-data.md#point-cloud-3d)).

### Why no compressed-mesh decoders

Draco and KTX2 (Basis) decoders ship as wasm loaded in workers; Meshopt's fast
path compiles wasm at runtime. Bundling them offline would need
`'wasm-unsafe-eval'` and `worker-src blob:`, which breaks the no-eval boundary.
Authors decompress with `gltf-transform` before compiling instead.

## Export

`ak-render export <spec> --format png|pdf --out <file>` captures the page in a
local browser: `--chromium <path>`, then `AK_RENDER_CHROMIUM`, then an installed
Chrome or Edge, then a Chromium Playwright already manages. Nothing is ever
downloaded. Driving the browser needs the `playwright-core` package, an optional
dependency that installs no browser; without it the export fails with
`driver-unavailable`. The page is served from a virtual origin with zero network
access; relative assets resolve only inside the spec's directory, or the working
directory when the spec comes from stdin.

`--scheme light|dark`, `--width <px>` (default 1440) and `--scale <1-3>`
(device pixel ratio, default 2) set the capture. `--format` alone decides the
bytes written, whatever the file extension. `--timeout <ms>` (at most 300000) is
one budget for the whole export.

Each 3D scene must draw a live WebGL frame. The exporter pins the high-quality
profile, freezes the first settled pose (reduced motion) and checks that every
scene produced a frame, so PNG and PDF carry the real scene. A failure has a
stable code (`usage`, `invalid-input`, `invalid-spec`, `browser-unavailable`,
`driver-unavailable`, `load-failed`, `timeout`, `webgl-unavailable`,
`scene-error`, `capture-failed`, `write-failed`) and leaves `--out` as it was;
the static plan is never passed off as an export. PNG output is byte-stable on
the same machine and GPU; a PDF embeds its creation time, so it differs on
every run.

`ak-render export doctor` lists every browser candidate, the driver, the
browser export would use and its WebGL 2 renderer.

### Export receipts

`--json` prints a receipt (`ExportReceipt` in `src/export/page-export.ts`). A
successful PNG of `fixtures/3d/scene-3d-basic.yaml` (paths shortened):

```json
{
  "ok": true,
  "format": "png",
  "out": "scene.png",
  "bytes": 1341543,
  "ms": 1308,
  "browser": { "source": "installed", "path": "<chrome.exe>", "version": "157.0.8103.38" },
  "renderer": "ANGLE (NVIDIA, ..., D3D11)",
  "quality": "high",
  "scenes": 1,
  "frames": [{ "width": 2108, "height": 1184 }],
  "blockedRequests": 0,
  "missingAssets": 0
}
```

Read it as evidence: `scenes` equals the 3D blocks on the page and `frames` has
one nonzero size per scene; `renderer` names the GPU (a SwiftShader or llvmpipe
string means software GL); `blockedRequests` counts requests the zero-network
origin refused, and `missingAssets` local files that were not found. A failure
exits 1 with a code and writes nothing:

```json
{ "ok": false, "code": "browser-unavailable", "message": "no browser at /nope/chrome (flag)" }
```

### Cloud export and asset consent

The hosted renderer's `POST /v1/screenshot`, `POST /v1/pdf` and
`artifact-export` capture a page through a Browser Run Quick Action
([cloud README](../apps/cloud/README.md#artifact-export)). For 3D pages:

- **Not verified.** That path has no export-ready wait, frame freeze or
  per-scene frame check like the local exporter, and a real WebGL 2 frame in
  Browser Run has not been proven. Treat a cloud PNG or PDF of a 3D page as
  unverified; it may show the static fallback. Use the local exporter when the
  live frame matters.
- **No asset upload.** The cloud compiles with no model or point-cloud
  resolver, so a block whose `src` is a local file fails there; inline data and
  allowed remote models are unaffected. Uploading local assets for a cloud
  export (an explicit, manifest-level consent before a temporary, owner-scoped
  private upload) is planned, not built, and nothing is uploaded today.

## Troubleshooting

| Symptom | Cause | What to do |
| --- | --- | --- |
| Block shows the drawing, `data-ak-3d-state="unsupported"` | No WebGL 2 (disabled GPU, blocklisted driver, remote desktop). | The fallback is the intended content. To get a live view, enable hardware acceleration or use another browser. |
| Export fails with `webgl-unavailable` | The capture browser has no WebGL 2. | Run `ak-render export doctor`; point `--chromium` at a Chrome or Edge that reports a renderer. The exporter already passes `--ignore-gpu-blocklist --enable-unsafe-swiftshader`. |
| Receipt `renderer` names SwiftShader or llvmpipe | Software GL (headless or GPU-less box, CI). | The export is still a real frame, only slower. Raise `--timeout` for dense scenes; do not compare its timings with a GPU run. |
| Export fails with `scene-error` | A scene reported `error` (model load, decoder, invalid edited config). | The message names the block; fix the asset or spec, then re-export. |
| Export fails with `timeout` | A scene did not settle inside `--timeout`. | Raise `--timeout` (max 300000), especially on software GL. |
| `model-3d` fails to compile | Local path outside the spec directory, unsupported extension or decoder, size cap. | Follow the diagnostic's `details.fix`; decompress with `gltf-transform`. |
| Print shows a drawing, not the canvas | Print uses the static fallback by design; export freezes the live frame. | Use `ak-render export --format pdf` for a live-frame PDF. |
| Nothing moves | Reduced motion is on, the block is offscreen, or the reader paused it. | Expected: content never depends on motion. |

## Mobile emulation limits

The browser tests and `pnpm bench:3d` run 375 and 768 px viewports with
Playwright's `isMobile` and `hasTouch` in desktop Chromium. That proves layout,
touch input and the `low` quality profile (a coarse pointer selects it). It
does not measure a phone's GPU, frame rate, memory, battery or thermal limits,
and no number from it is a real-device figure. Real devices are not part of the
release gates.

## Performance methodology

`pnpm bench:3d` (`tests/browser/bench-3d.spec.ts`, tagged `@bench`, outside
ordinary browser runs) measures, per fixture in its `FIXTURES` list and per
viewport (375 and 768 with mobile and touch emulation, 1440 at 1x and 2x):

- frame time p50/p95 over 120 animation frames, vsync-capped, so it shows
  dropped frames, not headroom;
- `renderer.render` CPU time p50/p95, after warm-up samples (shader compile
  included) are discarded; the runtime keeps the last 240 per scene, costs no
  measurable time and is never sent anywhere;
- draw calls and triangles from `renderer.info` (not GPU memory);
- quality profile and pixel ratio, context loss and restore, a 10-cycle
  mount/unmount leak check;
- PNG export reliability and latency over 5 runs, and the spec size and
  round-trips an agent spends (round-trips are assumed, and labelled so).

It fails only when draw calls or triangles drift from the committed baseline,
[benchmark-3d.md](artifacts/benchmark-3d.md) and `benchmark-3d.json`, which
`pnpm bench:3d:update` rewrites with browser, GPU, OS and CPU metadata. Timings
are informational: compare runs on the same machine, browser and GPU only, and
read a software-GPU baseline as a correctness record, not speed. Frame-time
budgets in planning documents are targets, not measurements.
