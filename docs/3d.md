# 3D blocks

`scene-3d` describes a 3D scene as typed data. The compiler inlines one shared
three.js runtime (generated by `pnpm three:generate`, checked by
`pnpm three:check`) only on pages that use a 3D block, so the page stays offline
and deterministic.

```yaml
- type: scene-3d
  title: Edge cluster
  summary: A core router linked to three edge nodes.
  bind: state.part
  objects:
    - { id: base, shape: plane, size: 6, rotation: [-90, 0, 0], tone: neutral }
    - { id: core, label: Core router, shape: icosahedron, position: [0, 1, 0] }
    - { id: rig, shape: group }
    - { id: edge-a, parent: rig, shape: box, position: [2, 0.5, 0] }
  timeline:
    - { target: core, property: rotation, to: [0, 360, 0], duration: 8000 }
```

## What the spec controls

- `objects`: up to 200, nested by `parent` at most 8 levels. Shapes, materials
  and tones are closed vocabularies; vectors are exactly 3 bounded numbers.
- `lighting`: a preset (`studio`, `soft`, `dramatic`, `night`).
- `camera`: position and target; omitted, the compiler frames the scene.
- `timeline`: rotation spins, position and scale ease back and forth.
- `views` + `viewBind`: a state value moves the camera and highlights an object.
- `bind`: picking an object (pointer, keyboard or the object list) writes its id.

There is no shader, script or raw asset input. `shader`, `glsl`, `wgsl`,
`vertexShader`, `fragmentShader` and prototype keys are rejected anywhere in a spec.

## scatter-3d

`scatter-3d` plots up to 20,000 points on real x/y/z axes. Data is columnar, so
a 20k-point spec stays compact; scalar columns (numbers or strings only) may hold
up to `maxColumnValues` (20,000) entries instead of the usual 200-item list bound.

```yaml
- type: scatter-3d
  title: Fleet load
  summary: Latency, CPU load and memory per host.
  bind: state.point        # a pick writes the point id
  filterBind: state.cluster # a legend click writes the group; "all" clears it
  axes:
    x: { label: Latency, unit: ms }
    y: { label: CPU load, unit: '%', min: 0, max: 100 }
    z: { label: Memory, unit: GB }
    size: { label: Requests, unit: k/s }
  groups:
    - { value: core, tone: accent }
    - { value: edge, tone: success }
  data:
    id: [h1, h2, h3]
    x: [12, 40, 33]
    y: [55, 72, 104]
    z: [8, 16, 12]
    size: [3, 9, 5]
    group: [core, edge, core]
```

- Scales: omitted bounds snap to 1-2-5 ticks around the data; explicit `min`/`max`
  are kept exact and points outside them are clipped (not drawn, flagged in the
  table and counted in the status line).
- Encodings: `group` colours by tone (up to 12 groups); otherwise `value` with
  `axes.color` uses a sequential ramp. `size` scales the point radius. Each
  encoding gets a legend.
- Interaction: click or `n`/`p` picks a point; drag with the Brush tool (or
  Shift-drag) brushes a region and fires `brush` with the count; Escape clears.
- Fallback: a full data table lists every point, so no-JS, print and screen
  readers see every value. The SVG poster uses the live camera.
- Rendering is one `Points` draw call with a lit sphere impostor shader.

## Fallbacks

The compiler projects every object through the same camera and emits a labelled
SVG plan plus an object list. That is what readers get without JavaScript,
without WebGL 2, in print and in screenshots of the source. With reduced motion
the live scene renders one still frame.

## Runtime

`window.akRender3d` exposes `mountAll`, `unmountAll`, `stats`, `freeze`, `sync` and `ready` for
tests and tooling. Scenes pause offscreen, recover from context loss and
release shared geometry on unmount. `html[data-ak-3d-quality="low|high"]`
overrides the automatic quality profile.

## Export

`ak-render export <spec> --format png|pdf --out <file>` captures the page in a
local browser: `--chromium <path>`, then `AK_RENDER_CHROMIUM`, then an installed
Chrome or Edge, then a Chromium Playwright already manages. Nothing is ever
downloaded. Driving the browser needs the `playwright-core` package, an optional
dependency that installs no browser; without it the export fails with
`driver-unavailable`. The page is served from a virtual origin with zero network
access; relative assets resolve only inside the spec's directory, or the working
directory when the spec comes from stdin.

`--scheme light|dark`, `--width <px>` (default 1440) and `--scale <1-3>`
(device pixel ratio, default 2) set the capture. `--format` alone decides the
bytes written, whatever the file extension. `--timeout <ms>` (at most 300000) is
one budget for the whole export.

Each 3D scene must draw a live WebGL frame. The exporter pins the high-quality
profile, freezes the first settled pose (reduced motion) and checks that every
scene produced a frame, so PNG and PDF carry the real scene. A failure has a
stable code (`usage`, `invalid-input`, `invalid-spec`, `browser-unavailable`, `driver-unavailable`,
`load-failed`, `timeout`, `webgl-unavailable`, `scene-error`, `capture-failed`,
`write-failed`) and leaves `--out` as it was; the static plan is never passed
off as an export. `--json` prints a receipt with bytes, timing, browser version,
WebGL renderer, frame sizes, missing assets and blocked requests. PNG output is
byte-stable on the same machine and GPU; a PDF embeds its creation time, so it
differs on every run.

`ak-render export doctor` lists every browser candidate, the driver, the
browser export would use and its WebGL 2 renderer.

## Benchmark

`pnpm bench:3d` measures frame-time p50/p95 (vsync-capped), `renderer.render` time p50/p95, draw calls and triangles (`renderer.info`, not GPU memory), the quality profile and pixel ratio, context loss and restore, a 10-cycle mount/unmount leak check and PNG export reliability for `fixtures/3d/scene-3d-basic.yaml` and `scene-3d-dense.yaml` at 375 and 768 (mobile and touch emulation) and 1440 at 1x and 2x. It fails when draws drift from the committed baseline, [benchmark-3d.md](artifacts/benchmark-3d.md) and `benchmark-3d.json`, which `pnpm bench:3d:update` rewrites with browser, GPU, OS and CPU metadata. It is tagged `@bench` and stays out of ordinary browser runs.

The runtime keeps the last 240 `renderer.render` times per scene for this benchmark (two `performance.now()` calls a frame); it costs no measurable time and is never sent anywhere.
